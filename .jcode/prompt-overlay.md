# AI-DLC on jcode

This project uses AI-DLC (AI-Driven Development Life Cycle) for structured development, running on the **jcode harness**. The workspace shell ships in `.jcode/` (no setup command); describe what you want to build and it sets up the workflow for you. Run `/aidlc` followed by a scope or project description to begin (a bare `/aidlc` only loads the skill, so add your request on the same line). Run `/aidlc --doctor` to validate your setup, `/aidlc --version` to print the framework version, `/aidlc --stage <slug>` to jump to a specific stage, `/aidlc --phase <name>` to jump to a phase, `/aidlc --depth <level>` to override depth, `/aidlc --test-strategy <level>` to override test volume, and `/aidlc --review <class>` to cap stage reviews (adversarial, advisory, none). Run `/aidlc compose "<task>"` to get a plan tailored to that task.

Your project's name, notes and rules go in `aidlc/spaces/default/memory/project.md`. Every AI tool in this project reads it.

## Prerequisites

- **jcode with AI-DLC support**: `jcode version --json` lists `hook_capabilities`; AI-DLC needs `project_hooks`, `project_trust`, `user_prompt_submit`, `prompt_origin`, `stop`, `swarm_identity`, `swarm_member_events`, `agent_definitions` and `skill_precedence_jcode` (`/aidlc --doctor` checks them).
- **Trust this project once**: jcode runs a project's hooks only after you approve them. In this folder run `jcode trust show` to review what AI-DLC registers in `.jcode/config.toml`, then `jcode trust grant` (add `--scope hooks` or `--scope agents` to approve one part). Editing that file asks for approval again.
- **Runtime**: Framework commands run through `aidlc`; keep that command and its runtime available. If `aidlc` is not found in this tool, give the person both fixes in one line, then end your turn without installing anything or working around it: if AI-DLC was installed while this tool was open, quit the tool fully and reopen it (a new tab or reloaded window is not enough); otherwise the installer's bin folder is not on PATH (an install with `-NoModifyPath`, or a Unix install whose PATH line was not applied), so add the folder the installer printed to PATH, or rerun the installer without `-NoModifyPath`, then reopen the tool.
- **Model/provider**: the shipped agent definitions pin no model. Your jcode configuration supplies the provider and default model; the personas ask for the coordinator's model (`model: inherit`), and the reviewers add a medium reasoning effort.
- **Auto-poke**: AI-DLC's stop hook keeps the forwarding loop going, so run `/poke off` in this project.
- **Locking**: Audit log file locking is handled portably using mkdir-based locking in the system temp directory (no external dependencies).
- **Hook permissions**: Framework hooks run through the self-contained `aidlc` binary. No separate script runtime or executable bits are required.

## AI-DLC Structure

- **Skill**: `.jcode/skills/aidlc/` — Orchestrator (`SKILL.md`), stage protocol, and the stage files across the phase directories (the enabled set depends on the composed plugins: see the compiled `.jcode/tools/data/stage-graph.json` or run `aidlc --doctor`)
- **Document skill** (user-invocable): `.jcode/skills/aidlc-knowledge/`, typed as `/aidlc-knowledge`; the framework CLI also exposes `aidlc engine knowledge <verb>`. Also standalone — outside the lifecycle graph — but classified `read-write`, unlike the read-only session skills below: it changes the document catalog and emits document audit events. It never advances the workflow stage pointer and never approves a gate. See "Document knowledge" under "Where things live" in the project's root `AGENTS.md` (Claude Code and Copilot readers find it under "Shared AI-DLC onboarding" in this file).
- **Session skills** (read-only, user-invocable): `.jcode/skills/aidlc-session-cost/`, `.jcode/skills/aidlc-replay/`, `.jcode/skills/aidlc-outcomes-pack/` — typed as `/aidlc-session-cost`, `/aidlc-replay`, `/aidlc-outcomes-pack`. Each pulls every count from `aidlc engine runtime summary --json` (no LLM-side counting). Classified `read-only`: they never advance the workflow stage pointer and never emit audit events. `aidlc-session-cost` and `aidlc-replay` print to the terminal only; `aidlc-outcomes-pack` is the only one that writes a file (`OUTCOMES.md`).
- **Stage-runner skills** (user-invocable): `.jcode/skills/aidlc-<stage>/`: one per runnable core stage, typed as `/aidlc-<stage>` (e.g. `/aidlc-domain-design`, `/aidlc-code-generation`); plugin-owned stages use their bare plugin-prefixed command name. Each runs that single stage in isolation via the engine's `--single` mode (`aidlc-orchestrate next --stage <slug> --single`) and **never advances your main workflow's `Current Stage`**: `next --single` records only the synthetic start boundary and `report --single` closes that same attempt. They are opt-in packaging: the same stage is reachable via `/aidlc --stage <slug> --single` without a runner. The runner set is generated from the compiled stage graph by `aidlc engine gen runners` and kept in sync by its `check` drift guard, so adding a stage file and regenerating adds its runner. The three bootstrap **initialization** stages ship no per-stage runner (they have no standalone meaning); the whole initialization phase is packaged as `/aidlc-init`: with `--scope <name>` and a description it creates the workflow record and its starting state in one step, with `--scope <name>` and nothing else it first asks what the work is for, and with only a description it first shows the same plan offer as describing the work. (This is opt-in packaging: describing what to build normally sets up the first piece of work by itself; no separate initialization command is needed.)
- **Agents**: `.jcode/agents/` — the base framework ships 14 agents: 11 domain-expert personas (product, design, delivery, architect, aws-platform, compliance, devsecops, developer, quality, pipeline-deploy, operations), 2 review-only agents (product-lead, architecture-reviewer), and the adaptive-workflows composer. A plugin install may add more; the enabled set is discovered from the files present under that directory. On jcode each expert role is an agent definition (`.jcode/agents/aidlc-<role>-agent.md`); the `/aidlc` session takes on those roles itself for most stages and hands work off through the `swarm` tool's `spawn` action (with `agent` naming the persona) for the delegated stages (2.1, 3.5), reviewer passes and Construction fan-out.
- **Sensors**: `.jcode/sensors/`: automatic checks that run on matching writes or once per existing deliverable at the approval gate. Gate-fired sensors may be advisory or blocking; blocking failures require an explicit audited override before the gate opens. Ships with framework defaults (`aidlc-claim-sources.md`, `aidlc-required-sections.md`, `aidlc-upstream-coverage.md`, `aidlc-traceability.md`, `aidlc-linter.md`, `aidlc-type-check.md`); forks may add custom `aidlc-<id>.md` manifests. Stages declare which sensors fire via the frontmatter `sensors: [<id>]` list — a pull import resolved at compile time.
- **Knowledge**: `.jcode/knowledge/` — Methodology reference. Per-agent under `aidlc-<agent>-agent/` subfolders; `aidlc-shared/` holds cross-agent material. Ships with framework.
- **Tools**: `.jcode/tools/`: small command-line programs (TypeScript sources invoked through the self-contained `aidlc` runtime) that do the parts which must be exact rather than judged: tracking where the workflow is, writing the decision log, deciding what runs next (`aidlc-orchestrate.ts`, with exactly six subcommands: `next`, `continue`, `report`, `park`, `team-board`, and `wait`; `continue` is internal steering transport and `team-board` is the read-only Team Construction query, and `wait` is the bounded read-only wait for dispatched work), running the automatic checks, recording what the team learned (`aidlc-learnings.ts`), and refereeing parallel Construction work (`aidlc-swarm.ts`). All framework files prefixed `aidlc-*.ts`.
- **Hooks**: `.jcode/hooks/`: scripts your CLI runs automatically at set moments, so the decision log, saved progress, and status display stay correct without anyone remembering to update them. All framework files prefixed `aidlc-*.ts`.

## Plugins

AI-DLC is open-world. Plugins under `plugins/<name>/` contribute additional stages, scopes, and agents, and `select-plugins` chooses which are enabled in this install. The counts above describe the base framework; your enabled set may differ. The compiled `.jcode/tools/data/stage-graph.json` and `aidlc --doctor` are the authoritative live view of what is enabled here.

## Guards

The guards are the person's checks. When the person asks in their own words to turn one of their checks off or back on, or to change the Guard Policy ("turn the review freeze check off for this project", "stop asking me to re-approve when files change", "relax the change checks", "turn it back on"), do it for them in the same turn and say the line the command prints, word for word, in your reply in that same turn, before any question, picker or next step (the command's output alone does not reach them): never refuse, never ask them to type it, and never investigate first. Asking for the guards or the checks as a whole to be off ("turn the guards off") is Guard Policy `off`, even when the same message also names one check. "Stop asking me to re-approve when files change" is Guard Policy `relaxed`, not one check; when Guard Policy is already `off`, say in one line that it is already off and change nothing. Turning a check on, or Guard Policy `strict`, is always fine; turning one off, or Guard Policy `relaxed` or `off`, happens only when they ask, never on your own and never as a suggestion. Where it applies is what they say: this piece of work, this project, or this machine. When they say neither, use this piece of work while one is open, otherwise this project; the line names where it applied. When the line ends with a question offering a wider place, that question is the only one: it is asked by saying the line, or by one picker carrying the same question instead, never both, and when they say yes, set it there yourself with the command from the table; a line that ends with no question asks nothing. For this piece of work run `aidlc engine config set <key> <on|off> --message <id>` with the key from the table and `<id>` the message they asked in. For this project run `aidlc config flags --bypass <switch> --local --yes --message <id>` (`--global` for this machine). To turn it back on, run `aidlc config flags --clear-bypass <switch> --yes`; when they name this machine or the project's shared settings, add `--global` or `--project` to clear it there. A `none` in the table means that place has no switch for the check: when they named no place, use the place it has; when they named a place it does not have, say in one sentence that it cannot be set there and offer the other place, and change it only when they agree. Guard Policy is set for a piece of work only; with none open, say so in one line. For Guard Policy run `aidlc engine config set guard-policy <strict|relaxed|off> --message <id>`; when the team holds Guard Policy strict in memory, it refuses with one line naming the file, and you say that line. A typed `/aidlc --guard-policy off` or `/aidlc config set guard.<fence> off` was applied when the message arrived. Never edit `aidlc-state.md` or run a hook to change a guard. `/aidlc --status` shows the current Guard Policy and every fence with where its setting came from. A remark about being careful with changes, or a question about a check, is not a request to change it; when you cannot tell, ask once.

## Models and effort

When someone asks in plain words to change an agent's model or effort ("make the developer agent think harder"), run `aidlc config models --agent <name> --effort <low|medium|high|xhigh|max> --project --yes`. For a model, use `--model <id>` in place of `--effort`, or both when they ask for both. Use `--local` instead of `--project` when it is only for them. If it asks for `--harness`, run it again naming this tool's harness. Print its output and stop. Never edit the `aidlc-*-agent` files for this.

## What's different on this harness

This is the same AI-DLC core that ships to every harness: the same ordered steps, the same approval gates, and the same written record of what was decided, rendered onto jcode. On jcode:

- Approval gates and questions render as **numbered prose options** (no structured-question widget); the questions FILE with `[Answer]:` tags remains the source of truth.
- Hooks are registered in the project's `.jcode/config.toml` and run only after `jcode trust grant`. They ride the AIDLC adapter (`.jcode/hooks/aidlc-jcode-adapter.ts`).
- The AI-DLC method (`aidlc/spaces/<space>/memory/*.md`) reaches each step through the engine itself: jcode has no include syntax for it.
- There is **no statusline**; use `/aidlc --status` and the progress lines at gates.
- Construction fan-out uses the `swarm` tool (`spawn` per unit with `working_dir` set to the unit's worktree, then `await_members`); `AIDLC_USE_SWARM=1` is a loud no-op.
- **MCP servers (optional)**: `.mcp.json` (project root, beside `.jcode/`) declares the MCP servers available to the framework. `context7` (library/SDK documentation lookups) is an HTTP server that reads `CONTEXT7_API_KEY` from your environment. The four AWS servers (`aws-mcp`, `aws-pricing`, `aws-iac`, `aws-serverless`) launch via `uvx` and authenticate with your standard AWS credential chain, so they need an AWS account with IAM credentials available to your shell (install `uv`/`uvx` via `curl -fsSL https://astral.sh/uv/install.sh | sh`). All credentials flow through environment passthrough and no keys are committed. Servers you have no credentials for are simply unavailable and never block a workflow.
- A workflow's `aidlc/` workspace tree is harness-neutral: a project can move between harness installs (supported but untested - keep the trees in sync via the framework's packaging if you do this).

The jcode-specific guide (install, what differs, verification) is `docs/guide/harnesses/jcode.md`.
